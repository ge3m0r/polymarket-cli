# 东京每日最高温研究原型

本原型把东京羽田机场的集合天气预报、实时观测和 Polymarket 每日最高温档位放在同一张表中。它是只读研究工具，不连接钱包、不下单。

## 使用

```bash
# 默认分析东京时间的明天
polymarket weather tokyo

# 指定日期
polymarket weather tokyo --date 2026-09-05

# JSON 输出
polymarket -o json weather tokyo --date 2026-09-05

# 手工加入站点偏差修正，例如模型长期比 RJTT 低 0.4°C
polymarket weather tokyo --date 2026-09-05 --bias-c 0.4

# 历史盈亏：默认75/25组合、最近14个连续事件，前一天00:15 UTC建仓，期望利润门槛1.5 USDC
polymarket weather backtest-tokyo

# 最近 30 个已结算事件
polymarket weather backtest-tokyo --recent 30

# 50% 旧版偏低四档 + 50% 完整分布优化器
polymarket weather backtest-tokyo --legacy-weight 0.5

# 指定日期、提前量、仓位和保守滑点
polymarket weather backtest-tokyo --since 2026-04-01 --until 2026-08-31 \
  --lead-days 1 --size 5 --entry-hour-utc 5 --slippage 0.01
```

输出包含：

- 各集合成员预测的当日最高温范围和均值；
- 按 Polymarket 温度档位统计的原始集合概率；
- 每个 YES 档位的最佳买价、卖价、taker 手续费、有效成本和扣费后 edge；
- RJTT 当天 METAR 最高温和最新报文；
- 全部 YES 档位的卖价、买价合计，用于检查完整集合对冲；
- JSON 模式下的 YES/NO token ID、市场 slug 和全部数据源。

`Net edge` 是 `模型概率 - YES best ask - taker fee`。它仍未扣除滑点、成交风险、模型校准误差或结算基差，不能直接视为交易信号。手续费参数从该市场当前的 Gamma `feeSchedule` 获取。

## 历史概率与盈亏回测

`backtest-tokyo` 从已结算的 Polymarket 东京最高温事件读取最终胜出档位，并使用 Open-Meteo Previous Runs API 中指定提前量的 GEFS 集合均值和离散度。算法不再围绕一个均值固定选择“下二上一”，而是：

1. 对 31 条重建成员轨迹分别取东京自然日内的最高温；
2. 按市场整数温度档位统计概率；
3. 枚举当天所有连续四档组合；
4. 用历史入场价格计算手续费后期望盈亏，以及每份再加 `--slippage` 的保守期望盈亏；
5. 选择保守期望盈亏最高的组合；若最高值不大于零，则当天空仓。

可用 `--legacy-weight` 混合旧版偏低策略。比如 `0.5` 表示一半资金买“预测最高温向下取整后，下方两档＋本档＋上方一档”，另一半资金买完整分布优化器选出的四档；重叠档位会自然叠加仓位。最终以混合组合的保守期望盈亏决定是否整组空仓。`0` 是纯分布优化，`1` 是旧选档加新风控门槛。

默认每档合计规模5份，在事件前一天00:15 UTC（东京09:15）取最接近的 CLOB 历史价格，并按当前天气市场公式加入 taker 手续费；保守期望利润低于1.5 USDC时空仓。事件通过 Tokyo Daily Weather 系列 ID `10740` 和 Gamma keyset 游标完整分页获取。

默认最近 14 个事件连续覆盖 2026-08-21 至 2026-09-03。未做偏差校准的结果为：14 天全部触发买入，四档仅命中 2 次；基础成本 17.805 USDC、兑付 10 USDC、净亏损 7.805 USDC，ROI -43.8%。每份额外加入 0.01 USDC 滑点后，成本 20.726 USDC、净亏损 10.726 USDC，ROI -51.8%。

这次结果推翻了旧版“固定下二上一”基线的乐观结论。主要原因不是四档宽度，而是这段样本中未校准 GEFS 分布整体偏高：即使组合在模型内覆盖率很高，实际胜出档位仍频繁落在其下方。后续必须用滚动窗口估计站点偏差，且只能使用交易日前已经发生的数据；不能用这 14 天全样本反向调参后再报告同一段收益。

| 0% | 100% | 14 / 0 | -7.805 | -43.8% | -10.726 | -51.8% |
| 25% | 75% | 14 / 0 | -5.128 | -18.6% | -8.040 | -26.3% |

|---:|---:|---:|---:|
| 0% | -51.8% | +1.5% | +6.6% |
| 50% | -13.9% | -9.4% | -6.2% |
| 75% | +0.8% | +0.3% | -1.2% |
| 100% | -0.3% | +5.5% | -3.3% |

没有一个固定权重在三个窗口内持续占优。纯分布策略在 60 期赚钱、最近 14 期却大幅亏损，说明模型误差或盘口定价存在明显阶段变化；50/50 在三个窗口都亏损，不能因为“中和”听起来稳健就继续作为默认候选。接下来应采用固定时间切分或逐日滚动的样本外验证，并增加模型偏差/市场状态过滤，而不是继续用全样本挑权重。

90期完整可用。六个月请求覆盖 2026-03-10 至 2026-09-03，但受集合均值历史档案起始时间影响，只有166期能匹配历史预报，其中163期能匹配入场价格；2026-03-31缺少对应事件。基础情形四组都为正，而加入每份0.01 USDC滑点后全部为负，说明观察到的毛优势很薄，主要结论是执行成本足以吃掉它。75/25在90期唯一保守盈利、六个月也亏损最少，但仍不能据此实盘。

### 一年 / 两年历史边界

使用 `--recent 365` 或 `--recent 730` 不会得到更多样本。完整查询仍只覆盖 2026-03-10 至 2026-09-03：166期匹配历史集合预报、163期匹配入场价格，2026-03-31缺少事件。75%旧策略 / 25%分布优化器的结果与上表六个月栏完全相同：基础 +10.670 USDC（+4.1%），每份加入0.01 USDC滑点后 -6.708 USDC（-2.4%）。

这是数据边界，不是 CLI 截断：Tokyo Daily Weather 可结算事件和 Open-Meteo 长期 ensemble mean/spread 档案都从 2026 年3月附近才形成。更早时期没有同一市场的真实盘口价格和结算事件，因此无法诚实计算“当时投入后的实际盈亏”。可以用 NOAA/JMA 历史天气做一至两年的模型准确率研究，但若为不存在的市场合成价格，所得只能称为压力测试，不能与当前资金回测合并。

### 最大样本盈利胜率（75%旧 / 25%新）

完整可用区间中有163期可作交易决策，策略交易84期、空仓79期。基础成交盈利58期、亏损26期，盈利胜率69.0%；每份加入0.01 USDC滑点后，盈利55期、亏损29期，保守盈利胜率65.5%。温度组合至少一侧覆盖胜出档位61次（72.6%），其中两侧都命中并获得完整5 USDC兑付36次，只有一侧命中并获得部分兑付25次。

保守场景平均每个盈利交易 +1.091 USDC，平均每个亏损交易 -2.300 USDC；总盈利59.984 USDC、总亏损66.692 USDC，profit factor 0.899。虽然65.5%的交易赚钱，但平均亏损约为平均盈利的2.1倍，盈亏平衡所需胜率约67.8%，所以最终仍净亏损6.708 USDC（-2.4%）。这说明胜率不能单独作为进入实盘的依据。

Open-Meteo 将 `_previous_day1` 定义为每个有效时刻前 24 小时发布的预测，避免使用事后更新值。Individual Ensemble API 的逐成员历史只保留约三天，因此这里使用长期保存的逐小时 ensemble mean/spread，以 31 个正态分位数重建成员，并假设成员排序在小时之间保持一致，再对每条轨迹取日最高温。这是可重复的历史分布近似，不是原始 31 成员的精确回放。

CLOB `/batch-prices-history` 提供历史价格序列，但不提供当时完整的 best ask 深度。基础结果把该价格作为入场代理；保守结果通过 `--slippage` 给四腿逐份加价。两者都假设四腿能够同时成交，因此真实执行通常不会优于保守结果。

### 买点与赔率敏感性

使用2026-03-10至2026-09-04的167个可匹配事件，固定75%旧策略、25%分布优化器、每档合计规模5份和每份0.01 USDC保守滑点，只改变事件前一天的历史价格时点。东京09:00共有163期可取价、交易90期，保守盈亏 +5.990 USDC、ROI +2.0%；东京10:00为 +5.046 USDC、+1.8%；东京11:00起整体转负。东京14:00的原配置为 -6.708 USDC、-2.4%。越接近事件日清晨，样本减少且结果继续恶化。

在东京09:15附近进一步要求保守期望盈亏至少1.5 USDC，167期中仅交易22期，12胜10负，保守盈亏 +7.423 USDC、ROI +15.2%，profit factor 1.384，最大累计回撤 -5.957 USDC。按时间前70%/后30%切分，留出段交易11期、7胜4负、保守盈亏 +5.098 USDC、ROI +18.6%。因此前向候选改为东京09:17和1.5 USDC门槛；样本仍小，不能宣称稳定盈利，必须继续用不可变实时盘口快照验证。

## 前向模拟收益账本

云端 `signal-tokyo` 在计划买点通过一次公开 CLOB `/prices` 批量请求直接读取 YES 最佳卖价，随后立即冻结 JSON 快照，记录报价时间、延迟、所有入选档位的 `best ask`、份数、手续费及保守滑点成本。买点为 UTC 00:17（东京前一天09:17），保守期望盈亏至少为1.5 USDC才模拟买入；只有计划时间后15分钟内的快照属于标准样本，其他手动或延迟运行只用于诊断，不计入收益。

次日 `settle-tokyo-paper` 使用 Polymarket 已结算胜出档位结算原始快照。云端任务通过只读仓库权限在连续的 `tokyo-weather-paper-ledger` Artifact 之间滚动保存 `paper-signals/open/` 和 `paper-signals/settled/`，不会自动提交主分支。结算后的实际盈亏不会调用历史价格接口，也不会用结算后的价格倒推买点。前向账本与使用价格代理的历史回测必须分别统计。

## 去年同日温度参考

实时 `weather tokyo` 输出增加 Open-Meteo Historical Weather API 的去年同日最高温。它用于检查季节性和异常天气，例如当前模型显著偏离去年同日时提示进一步检查；它不直接与今年预报取平均，也不单独决定下注档位。

选档顺序建议为：今年最新集合概率为主，去年同日温度作弱先验，最后用四档含费成本做交易门槛。如果包含去年温度的区间在今年集合中概率过低，或组合成本高于模型覆盖概率，应放弃而不是为了纳入去年温度强行扩大区间。

## 数据源选择

### 1. 权威结算源：NOAA WRH RJTT

Polymarket 当前东京市场以 NOAA 的 `RJTT`（Tokyo Haneda Airport）逐时页面为结算源：

```text
https://www.weather.gov/wrh/timeseries?site=rjtt
```

市场规则说明会在指定自然日结束、下一日首个数据点发布后结算，并以页面记录的整数摄氏度最高值判断档位。任何模型或辅助观测都不能覆盖具体市场 `description` 中的规则。

用途：最终标签、结算核对。

### 2. 主预测源：Open-Meteo Ensemble API

实时原型默认使用 `gfs_seamless`，请求羽田机场坐标附近的全部 `temperature_2m` 集合成员，再计算每个成员在东京自然日内的最高温。历史回测默认使用 `ncep_gefs_ensemble_mean_seamless` 的归档均值和离散度。

```text
https://ensemble-api.open-meteo.com/v1/ensemble
```

优点：统一接口、无需密钥、直接返回各集合成员，适合快速形成概率分布。

限制：它是模型数据聚合和插值服务，不是结算源；返回的网格点也不一定正好落在机场观测设备上。

可通过 `--model` 测试其他 Open-Meteo 模型标识。切换模型前应先在其文档中确认覆盖范围、更新时间、集合成员数和授权条件。

### 3. 盘中观测：NOAA AviationWeather METAR

原型读取 RJTT 最近 30 小时的 METAR：

```text
https://aviationweather.gov/api/data/metar
```

用途：确认当天已经出现的最高温，避免模型仍给低于已观测温度的概率。

限制：METAR 是实时交叉检查，不等同于最终结算页面；观测可能修订，采样频率和取整也会影响最高值。

### 4. 校准标签：日本气象厅羽田历史观测

日本气象厅提供羽田的日值、10 分钟值以及航空气象观测月表/年表，适合研究海陆风、机场站偏差和季节性误差。

用途：历史站点偏差估计、质量复核。

限制：JMA 历史最高温与 Polymarket 指定 NOAA 页面在采样和取整上可能不完全一致，最终回测标签仍应优先保存实际结算源快照。

### 5. 后续模型源

建议按以下顺序扩展：

1. NOAA GEFS：全球集合概率基线；
2. ECMWF IFS Ensemble：第二个独立集合源；
3. JMA GSM/MSM/LFM：日本区域模型，LFM 对羽田短临尤其有价值；
4. TAF：航空预报辅助变量，不直接提供可靠的每日最高温概率。

不同模型不能简单把成员全部拼在一起。应先对每个模型单独做历史偏差与离散度校准，再做加权组合。

## 对冲结构

### 同一二元问题：YES 与 NO

每个温度档位本身都是一个 YES/NO 二元市场。持有某档位 YES 时，买入同一档位 NO 可以锁定结算总回报 1，但买入成本、手续费和价差通常会把锁定收益变成亏损。更直接的退出方式通常是卖出已有 YES。

JSON 输出为每一档提供 `yes_token` 和 `no_token`，可分别查看订单簿：

```bash
polymarket clob book <YES_TOKEN_ID>
polymarket clob book <NO_TOKEN_ID>
```

### 同一天全部温度档位：完整集合

东京每日温度事件通常由 11 个互斥且穷尽的 `negRisk` 档位组成，例如 `≤21°C`、`22°C` 到 `30°C`、`≥31°C`。如果规则确实保证恰好一个档位为 YES，那么每档各持有 1 份 YES，最终总回报固定为 1。

原型计算：

```text
complete_set_ask = 所有 YES 最佳卖价之和
gross_buy_all_edge = 1 - complete_set_ask

complete_set_bid = 所有 YES 最佳买价之和
gross_sell_all_edge = complete_set_bid - 1

complete_set_effective_cost = complete_set_ask + 各腿 taker fee
net_buy_all_edge = 1 - complete_set_effective_cost
```

只有所有档位都有可成交报价、属于同一个 `negRiskMarketID`、数量一致，并且扣除手续费和滑点后仍为正，才可能形成可执行机会。逐腿成交会暴露 leg risk，不能把报价之和自动当成套利。

Polymarket NegRisk 合约还允许把同一互斥市场中的多份 NO 转换为互补 YES 和抵押品，但当前 CLI 没有暴露通用 `convertPositions` 命令，因此原型只做发现和计算，不执行转换。

### 相邻温度档位

同时持有相邻档位（例如 25°C 与 26°C YES）可以降低一档预测误差，但不是无风险对冲：如果最终落在其他档位，两份都归零。它更接近“扩大命中区间”。

### 跨城市市场

东京与首尔、上海、北京等温度受同一天的大尺度天气系统影响，但观测站、海陆风、时区、云量和局地降水不同，只能作为统计对冲，不能锁定收益。

建立跨城市对冲前至少需要：

- 相同预测提前量下的历史残差相关性；
- 极端天气期间的相关性稳定性；
- 两边订单簿深度和手续费；
- 基于温度偏差而非绝对温度的标准化头寸。

第一阶段不建议使用跨城市实盘对冲。

## 当前模型边界

- 集合成员频率未经概率校准，31 个成员只能给出较粗的概率刻度；
- 网格最高温与 RJTT 机场站最高温存在系统偏差；
- `.round()` 只是把模型温度映射到整数结算档位的第一版近似；
- `bestBid`/`bestAsk` 是快照，不保证下单时仍可成交；
- 完整集合指标未扣除天气市场 taker fee；
- 暂未保存预测 run time，不能用于无前视偏差的历史回测。
